# Phase 2 v37 — withdrawal / notification / account-boundary cross-audit (2026-11-18)

## Scope and method

Source-only static audit based on the v36 candidate tree. No database connection, SQL execution, build, test, lint, typecheck, local checks, LINE delivery, or remote mutation was performed. This batch adds no migration and does not change application/runtime source: the unresolved paths require actor attribution, dual-role lifecycle decisions, or target-schema/transaction-contract verification; adding a generic trigger would risk notifying the withdrawing actor or silently altering refund semantics.

## Findings (20 checks)

### P1 — resolve before limited release

1. **Dual-role withdrawal is regressed by the later replacement function.** `20261114_006_withdrawal_dual_role_direct_invite_refunds.sql` explicitly discovers both `performers` and `facilities` profiles (`v_is_performer` / `v_is_facility`). Later `20261116_013_cancel_reapply_and_direct_fee_refund.sql` replaces `withdraw_user_account(text)` and branches on `v_user.user_type` only. A user with both profiles therefore follows only the primary role's cleanup/refund path. This is a direct source-level incompatibility, not a live-DB assertion.
2. **Lesson withdrawal cleanup is primary-role gated.** `20261118_011_close_pending_lesson_applications_on_withdrawal.sql` only runs when `NEW.user_type='performer'`. A dual-role account whose primary type is `facility` can retain pending lesson applications/offers when the performer profile is also being withdrawn.
3. **The dual-role function replacement also changes profile anonymization coverage.** Migration 013's branch-specific cleanup updates only the profile matching `user_type`; the earlier 006 implementation used actual profile existence flags. The non-primary profile may remain populated after withdrawal.
4. **Withdrawal notification wrapper inherits the primary-role limitation.** `20261116_021_withdrawal_notification_outbox.sql` wraps the later `withdraw_user_account`; it cannot restore the missing second-role cleanup and only emits the match/direct-invite payloads returned by that function.
5. **Lesson application status transitions on withdrawal are not notified.** Migration 016 registers only `AFTER INSERT` on `lesson_applications` and updates to `lesson_offers`; migration 011 changes pending lesson applications to rejected without an Outbox event. The correct counterpart depends on whether the withdrawing user owns the offer or submitted the application. A generic trigger cannot safely infer/omit the actor from the current row update.
6. **Band invitation cancellation during withdrawal is not notified.** Migration 022 only handles pending→accepted/rejected; withdrawal changes pending invitations to `cancelled` in migration 013. The event needs the actual withdrawing performer to select only the counterpart; current trigger arguments do not carry that actor.
7. **Band disband/member departure has no counterpart notification.** Withdrawal disbands leader-owned bands and changes active memberships to left, but the inspected notification migrations cover invitation create/response, not disband or member departure. Recipients and message semantics need explicit policy before adding transactional events.
8. **Ordinary application rejection on withdrawal has incomplete notification coverage.** Withdrawal changes pending applications to rejected (facility-owned and performer-owned, plus applications in disbanded bands); existing application notification logic covers create/expiry but does not provide actor-aware counterpart cancellation notifications.
9. **Outbox scheduled drain is low frequency and bounded.** `vercel.json` schedules `/api/cron/line-notification-outbox` once daily at `05 02 * * *` (11:05 JST), and the route drains five rows. The shared drain helper clamps batches to five. This can leave notification backlog for many hours under bursts or transient failures. Schedule changes depend on the deployed Vercel plan and operational limits; no schedule change was made.
10. **Expiry processing is also once daily and bounded.** `vercel.json` schedules expiry once daily at `01 00 * * *` (10:00 JST). The RPC can process up to 5,000 rows per invocation; if the due backlog exceeds that, remaining attempts wait for the next daily run. Capacity and actual backlog require live operational data.

### P2 — policy/verification required

11. **Band transfer idempotent replay precedes current membership/account checks.** Migration 014 returns the previous result once both idempotency ledger rows match, before checking current band status, membership, and active accounts. It does not debit twice, but a replay after withdrawal/removal can still return `success=true` for a historical transfer. Decide whether replay should report historical success or current authorization failure; preserve no-double-debit semantics either way.
12. **Band transfer replay integrity depends on both ledger rows.** The RPC correctly rejects one-sided ledger state and mismatched amount/participants/description/band, but there is no source-side repair path; recovery is manual/admin-only. Keep fail-closed and document operational reconciliation.
13. **Band transfer balance overflow is checked for recipient only.** Sender underflow is constrained by available balance and reserved lesson coins; recipient integer overflow is explicitly checked. Verify the database column types and any balance constraints in the target schema before applying migration 014.
14. **Profile/avatar persistence remains multi-transaction.** Performer POST updates `users.avatar_*` before inserting/updating `performers`; facility POST/PATCH similarly update `users` and `facilities` separately. A later write failure can leave avatar and profile state inconsistent. Atomic RPC requires confirmed unique constraints, full field schema, and response compatibility; no speculative RPC was added.
15. **Facility PATCH updates profile and avatar in separate REST requests.** Profile data can commit while avatar update fails, or vice versa depending on request ordering. The route reports the avatar error after the facility update, so the client can receive failure despite a committed profile change.
16. **Performer POST follows the same partial-commit risk.** Avatar update succeeds before performer profile persistence. Retry can repair some cases but is not an atomic guarantee.
17. **Band invitation GET is a multi-query read.** It loads invitation rows, then band and performer details in separate calls. The source applies active-account auth to the caller, but counterpart profile rows are not all filtered by active account in the detail enrichment query. Verify intended historical visibility for withdrawn counterpart names and anonymization policy.
18. **Band detail read performs multiple independent reads.** Band, membership, and performer rows are fetched separately. The initial caller active-account check and membership check exist; concurrent membership changes can produce a mixed snapshot. Treat as a consistency issue, not a direct authorization bypass, because mutation RPCs enforce membership separately.
19. **Band transfer page read is multi-query.** It reads user, band, own membership, all memberships, performers, and transaction history in separate calls. It filters the caller to active and requires membership, but a concurrent leave/disband can cause stale display. Mutation RPC remains the authority.
20. **Withdrawal API drains Outbox synchronously after the transaction.** The RPC commits withdrawal and Outbox rows first, then the route attempts immediate delivery. Delivery failures do not roll back withdrawal; this is correct for transactional safety, but the response reports aggregate delivery counts rather than per-event state. The daily worker remains the recovery path and needs operational monitoring.

## Recommended order

1. Reconcile `withdraw_user_account` once, preserving the migration 013 refund/attempt lifecycle while restoring both-profile discovery and cleanup from 006. Include lesson cleanup and the notification wrapper in the same reviewed contract.
2. Add actor-aware Outbox payloads for ordinary applications, lesson applications, band invitation cancellation, band disband, and membership departure. Do not use a generic status trigger that can notify the actor.
3. Decide Outbox latency target, cron cadence, bounded batch size, retry visibility, and duplicate-delivery policy based on the actual Vercel plan and LINE constraints.
4. Design transactional profile/avatar RPCs only after schema/unique-key and API response contracts are verified against the intended Tokyo database.
5. Decide historical idempotency replay response semantics; do not weaken the two-ledger fail-closed check or permit a second debit.
